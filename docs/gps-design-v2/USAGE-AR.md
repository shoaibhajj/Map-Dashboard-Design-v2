# دليل الاستخدام — مهام جديدة وتعديلات قديمة دون بيروقراطية

## الفكرة

اشرح ما تريد طبيعياً. لا تحتاج حفظ ثمانية أوامر أو كتابة كل تفاصيل التصميم. طبقة التوجيه تختار المسار المناسب، ويمكنك تحديد المهارة صراحة عندما تريد تحكماً أكبر.

Context يجيب «ما الهوية وما القواعد؟». Skill يجيب «ماذا نفعل الآن، وبأي ترتيب، وأين نتوقف؟».

## اختيار المهارة

| طلبك | المسار |
|---|---|
| غيّر الدائرة لسهم صغير | gps-design / micro |
| صمّم إنذارات للمشاكل المهمة على الخريطة | gps-design + قسم alarms؛ gps-explore فقط إن كانت الفكرة مبهمة |
| أريد تخصيص مكونات Dashboard | gps-design / behavior-rich + DASHBOARD |
| ابتكر clustering غير مشابه للمثال | gps-explore ثم gps-design حسب التفويض |
| هذا مكوّن من 21st.dev أريده بلغتنا | gps-adapt |
| أريد مشهداً ثلاثي الأبعاد لمستشعر/مركبة | gps-dimension، ثم تنفيذ إذا كان مطلوباً |
| راجع فقط | gps-review؛ لا كتابة ولا تعديل |
| سجّل هذا النمط | gps-imprint capture |
| دقّق اتساق صفحة المركبات | gps-imprint audit، لا تصحيح تلقائي |
| المحاولات صارت أسوأ | gps-recover |
| احفظ ما وصلنا إليه / استعده | gps-handoff save / restore |
| احسب نسبة أو اشرح خوارزمية دون تغيير واجهة | بدون Skills/Context التصميم |

لا تنفّذ كل الجدول لكل مهمة. استشارة checklist من مهارة مساعدة لا تعني إعادة التخطيط من البداية.

## أوضاع الطلب

### افهم/اقرأ فقط

```text
اقرأ الفكرة والملف المرفق فقط. لا تصمم ولا تنفذ ولا تحدث السجلات الآن.
```

### استكشاف فقط

```text
استخدم gps-explore لابتكار 3 اتجاهات لعرض clusters. أريد المفاهيم فقط قبل التنفيذ.
حافظ على حساب التجمعات الحالي. المثال مرجع للفهم وليس للشكل النهائي.
```

### تنفيذ مباشر بمرونة

```text
اختر معالجة مناسبة للهوية ونفذها داخل [المكان]. يمكنك اتخاذ القرارات الجمالية
القابلة للتراجع، لكن لا تغيّر منطق البيانات أو تضف dependency دون المراجعة اللازمة.
```

هنا لا يتوقف الوكيل طلباً لموافقة على كل ظل ومسافة. تبقى القرارات الجوهرية غرضاً للسؤال.

### تنفيذ محدد

```text
نفذ هذا الشكل/السلوك بالضبط ضمن [المكوّن]. لا توسع المهمة ولا تقترح إعادة تصميم الصفحة.
```

## عندما يكون الطلب غير محدد

يستخلص الوكيل الوظيفة والهدف والتأثير المطلوب. لا يسأل عما هو محسوم مثل الهوية والثيم. يسأل فقط عندما يتغير التصرف الصحيح: ما critical؟ هل الحفظ محلي أم لكل حساب؟ هل اتجاه السهم يمثل heading؟

لا ينبغي أن يسأل «أي درجة نعناعي؟» قبل كل مهمة، ولا أن يختلق قراراً متعلّقاً بالأمان لأنه لم يسأل.

## دورة عملية مقترحة، لا سلسلة إجبارية

1. اشرح الهدف والمكان وما تريد الحفاظ عليه.
2. التنفيذ الصغير يبدأ مباشرة بعد الفحص؛ المهم/المبهم يحصل على brief ومفاهيم مناسبة.
3. راجع النتيجة في البيئة الحقيقية، وليس screenshot فقط إن كانت فيها حركة.
4. اطلب gps-review للمراجعة المستقلة عند الحاجة.
5. إذا أعجبك النمط قل ما الذي اعتمدته تحديداً، ثم اطلب capture.
6. احفظ handoff عند التوقف عن مهمة طويلة.

«جميل» قد يعني رضا عن لقطة، لا اعتماد جميع المكونات والمقاسات للمنصة كلها. كن محدداً في الاعتماد: هذا نمط مؤشرات المركبات، أو هذا المشهد للـHero فقط.

## التعامل مع النتائج

الوكيل يجب أن يذكر: الفكرة، الملفات المتغيرة، الوظائف المحفوظة، القرارات المهمة، ما اختُبر وما لم يُختبر. لا تصدّق «سريع» أو «جاهز للإنتاج» إن لم يتبعها دليل مناسب.

إذا خرجت الفكرة عن الاتجاه، صف البعد المرفوض: glow يحجب الخريطة، شكل عام جداً، تفاصيل IoT غير مفهومة، حركة زائدة، كثافة ضعيفة، أو تغير وظيفة. استخدم gps-recover بدلاً من إضافة «اجعله مذهلاً أكثر» في كل محاولة.

## لا تلوّث مهام أخرى بالهوية

- «احسب متوسط 10 قراءات» → حساب مباشر بالطريقة المناسبة، لا BRAND ولا UI review.
- «حسّن خوارزمية clustering فقط» → هندسة/اختبارات بيانات؛ لا تغيير شكل التجمع.
- «غيّر عرض نتيجة الحساب في Widget» → هذه الواجهة فقط تدخل مسار التصميم.
- «أصلح خطأ API» → مهارات الهندسة المناسبة؛ لا طلب أنيميشن أو 3D.
- «غيّر مؤشر المركبة» → لا توليد صفحة تسويق جديدة.

تكرار كلمة GPS أو IoT في السؤال وحده ليس سبباً لتفعيل منظومة التصميم.
