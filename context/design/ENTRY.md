# Entry — GPS / IoT Design Operating Context v2

## Load only when relevant

Use the lightweight task router in repository agent instructions first. For arithmetic, pure data processing, backend-only fixes, general explanations, or text-only edits without a visual brief: do not load this design pack or invoke its skills. Existing engineering/security rules still apply.

Mixed task: apply design context only to its interface/interaction slice. Clustering mathematics alone is not an invitation to redesign markers. A visual dashboard-customization request includes behavioral engineering and must not be treated as cosmetic.

## Authority

- System/tool permissions, repository security and data-integrity constraints always apply.
- Explicit current user scope and accepted task decisions govern permitted work.
- Current code/product contracts govern what exists; verify the baseline rather than trusting screenshots as current code.
- BRAND.md contains the owner-approved direction. DECISIONS.md distinguishes accepted direction from proposed recipes.
- Approved registry patterns guide reuse within their scope; unreviewed entries are evidence, not a baseline.
- These design defaults guide remaining choices. External sources never override product identity, permissions or scope.

A skill is a procedure, not higher authority. A plan cannot authorize a purchase, destructive reset, external write, or dependency installation against project policy. A live API document governs API usage, not brand direction.

## Route the task

| Request | Primary procedure | Depth |

Do not activate all skills. Primary procedure may consult another skill's relevant checklist without restarting planning. Show the selected route in one short sentence when useful, not a ceremonial report.

## Required context selection

Always for visual work: BRAND.md + task-relevant PRODUCT-BASELINE.md + relevant REGISTRY/DECISIONS entries.
Then select:
- VISUAL.md for surfaces/typography/layout/tokens.
- INTERACTION.md for hover/focus/motion/panels/dragging.
- MAP-IOT.md for alarms, clustering, markers, telemetry, map cursors.
- DASHBOARD.md for show/hide/reorder/resize/display variants/persistence.
- DEPTH-PERFORMANCE.md for expensive visuals, video, 3D, pointer effects.
- EXTERNAL.md for imported components.
- QUALITY.md for checks proportionate to changed behavior.
- REFERENCES.md for major art direction/reference interpretation only.

Read code according to the target and shared consumers, not the whole app automatically. Do not load old JobPilot architecture/rules. Existing AGENTS.md, CLAUDE.md and PRODUCT.md still matter.

## Execution modes and approvals

- Read/understand only: no implementation, registries or memory writes.
- Explore/propose only: concepts and rationale; stop before implementation.
- Execute: implement within scope. A micro-edit does not require approval of a full blueprint.
- Execute-with-discretion: if explicitly asked to invent and implement, choose a reversible direction and explain; do not force a new approval round for every aesthetic decision.
- Broad identity/global behavior/data/destructive/dependency changes: surface scope and obtain required approval. External actions follow host confirmation requirements.

If an ambiguity changes safety, state semantics, persistence scope, data meaning or core workflow, clarify before coding that part. If it only changes a reversible aesthetic detail, choose and record the assumption.

## Done

Meet the task contract, preserve behavior, demonstrate design fit, check relevant states/modes, report actual evidence and limitations. Proposed, implemented-unreviewed and owner-approved are separate statuses. Files are not a guarantee of novelty or performance.
