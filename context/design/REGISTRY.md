# Design Registry — observed, implemented and approved are different

## Initial state

No new component implemented by this v2 pack. No alarm system, customization engine, cursor or marker redesign is completed merely because docs exist. Existing component inventory remains task-local until inspected.

## Entry status

observed-existing / proposed / implemented-unreviewed / owner-approved / needs-revision / superseded.

Only explicit owner acceptance of a pattern can promote it to owner-approved; record evidence/scope/date. The approved brand direction does not approve all UI implementations. A later accepted task updates only its own pattern unless broader adoption is explicit.

## Rules

Record purpose and invariants, not exact classes as universal law. Keep concrete implementation references so the pattern is reproducible; allow contextual variants. Many radii aren't automatically conflicts when roles differ. Hardcoded data-visualization/map values may need review, not blind replacement with one accent.

Update only relevant entries; preserve supersession history. Do not duplicate the entire context or implementation. No secret-bearing paths/URLs/data. Future agents check approved entries AND current code before reuse. Use gps-imprint for capture/audit; audit reports do not auto-write a baseline.
